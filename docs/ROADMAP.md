Идеи и приоритеты новых фич. Составлен 2026-07-03 по итогам сравнения с amoCRM / Bitrix24 / Salesforce и анализа процессов онлайн-школ. **Сводный статус «реализовано / осталось» — [ROADMAP-full.md](ROADMAP-full.md)**; здесь — подробные описания фич.

## Утверждённые волны разработки

### Волна 1 — деньги ✅ ГОТОВО (июль 2026)

1. **A3. Платёжные ссылки + webhook оплаты.** ✅ **CloudPayments + Робокасса** за общей абстракцией (`services/payments/`, ЮKassa — позже добавляется новым провайдером): кнопка «Выставить счёт» в DealModal (пакет из справочника + ручная корректировка суммы/уроков) → ссылка копируется или уходит клиенту через существующий мессенджинг → идемпотентный webhook (`/api/webhooks/payments/*`, подписи от сырого тела) → Payment succeeded → автосоздание абонемента из снапшота → автоперенос сделки в «Оплачено» (настройка `/settings/payments`, фолбэк — первый won-этап) → триггер `payment_received`.
2. **A1. Абонементы / пакеты уроков.** ✅ Модели `Package/Subscription/Lesson`: справочник тарифов (`/settings/packages`), подписка у контакта со ссылкой на сделку, списание за `completed` И `no_show` (`canceled` не списывает) транзакцией с защитой от двойного клика, урок с преподавателем (роль `teacher`). Триггер `subscription_low_balance` (порог настраивается, срабатывает один раз при пересечении). Баланс виден в DealModal и на странице контакта.

Зависимость волны: **B1. Статусы won/lost + причины отказа** ✅ — `Stage.type: open|won|lost` (бэкфилл последнего этапа как won), справочник `LostReason`, `Deal.lostReasonId/lostComment/closedAt`, диалог причины при переносе в lost (канбан + карточка), аналитика won/lost/winRate + разбивка потерь по причинам.

Осталось руками после деплоя: боевые креды CloudPayments и Робокассы в `/settings/payments`, URL вебхуков в ЛК провайдеров (`{API_URL}/api/webhooks/payments/{cloudpayments|robokassa}`), контрольный платёж 1–10 ₽ (у CP тестового магазина нет; Робокасса — режим IsTest).

### Волна 2 — верх воронки ✅ ГОТОВО (июль 2026)

3. **A2. Workflow пробного урока.** ✅ Модель `TrialLesson`, запись/перенос/результат из DealModal, напоминания в выбранный менеджером канал (WazzUp: whatsapp/telegram/tgapi/max/maxbot/vk + SMS через TargetSMS), настраиваемые офсеты и шаблоны (`/settings/trials`), show-rate в аналитике, триггеры `trial_booked`/`trial_completed`/`trial_no_show` для реактивационных цепочек.
4. **A6. Форма захвата лидов.** ✅ Публичный `POST /api/leads` (секретный ключ, rate limit, UTM → custom_fields, дедуп контактов по телефону), настройка на `/settings/lead-form`. По решению пользователя — только API-endpoint, без hosted-страницы.

Зависимость волны: **B3. Timer-триггер** ✅ — «сделка в этапе дольше N часов», delayed-джобы в очереди `automations` с guard-ами по `Deal.stageEnteredAt`.

Осталось руками после деплоя: креды TargetSMS в `/settings/sms`, `SCHOOL_TZ` в `.env` на сервере.

**B12. Раздел «Чаты».** ✅ ГОТОВО (июль 2026). Единый инбокс мессенджеров (WazzUp-каналы + SMS,
без email — для него отдельный раздел «Почта», см. C5): список чатов слева (последнее сообщение,
непрочитанные), окно переписки справа. В отличие от «Почты» группировка не по `threadKey`, а по
`contactId` — один чат = один контакт со всеми его каналами. Роуты `routes/chats.ts`; видимость
чата по `assigneeId` сделок контакта, админ видит всё (`services/chats/access.ts`); только ответ в
уже существующую переписку — холодная отправка первого сообщения по-прежнему через
`NewMessageDialog` в карточке сделки. Общий хелпер отправки `services/messaging/sendToContact.ts`
переиспользуется и картой сделки, и «Чатами». Сокет-комнаты `chats:inbox`/`contact:{id}`; заодно
пофикшен вебхук WazzUp — `NEW_MESSAGE` теперь эмитится и без `dealId` (раньше входящее от
контакта без активной сделки тихо сохранялось в БД, не всплывая в интерфейсе). **Осталось**:
сообщения без `contactId` (несматченные вебхуком) в раздел не попадают; пагинация и поиск по
чатам не реализованы (паритет с «Почтой» — там тоже нет).

### Волна 3 — инструменты (июль 2026) — ЧАСТЬ ГОТОВА

5. **B2. UI-конструктор автоматизаций.** ✅ ГОТОВО. `components/automation/AutomationDialog.tsx` —
   один диалог на создание/редактирование, вызывается со `settings/automations/page.tsx`; выбор
   триггера + цепочка действий (`create_task`, `send_wazzup_message`, `change_field`, `move_stage`,
   `notify_user`) с динамическими полями по типу и клиентской валидацией обязательности (бэкенд-схемы
   permissive, ничего не требуют сами). `move_stage` даёт выбрать этап любой воронки — движок умеет
   кросс-воронковый перенос. Бэкенд не менялся — движок и CRUD-API были готовы заранее.
6. **B4. Импорт CSV и Excel + экспорт.** ⏳ ЧАСТЬ ГОТОВА — реализован только экспорт.
   ✅ Экспорт сделок: `GET /api/deals/export?format=csv|xlsx` (только `admin` — выгрузка отдаёт
   данные по всем менеджерам разом, а ролевой видимости «своё» в проекте нет нигде), кнопки на
   `/deals`. Колонки — все поля сделки и **полные данные привязанного контакта, включая его ID**,
   плюс кастомные поля обеих сущностей человекочитаемыми значениями (`select`/`multiselect` через
   `field.options`, не сырой value). CSV — `csv-stringify` с BOM (кириллица не бьётся в Excel),
   XLSX — `exceljs`. Прямое blob-скачивание (`responseType: 'blob'` + `URL.createObjectURL` + `<a
   download>`) — новый паттерн, раньше в проекте был только signed-URL-скачивание для email-вложений.
   Дополнено (июль 2026): роут принимает `ids` (через запятую) — экспорт только выбранных чекбоксами
   сделок, игнорируя остальные фильтры (см. B14).
   ❌ Импорт (миграция из amoCRM: загрузка файла → маппинг колонок на поля, в т.ч. кастомные →
   массовое создание contacts/deals) — не начат, отдельная итерация.
   ❌ Экспорт контактов/компаний отдельно от сделок — не начат, только сделки в этой итерации.
7. **B13. Управление пользователями и ролями.** ✅ ГОТОВО (июль 2026). Модель `Role`
   (name/permissions[]/isSystem) с 12 ключами прав (`packages/shared/src/constants/permissions.ts`),
   `User.roleId`+`User.active` (строковая колонка `User.role` удалена). `requirePermission()`
   заменил `requireRole()` почти везде (~40 роутов, кэш прав 60с по userId); новые гейты
   `entities.edit` (мутации deals/contacts/companies), `section.analytics|email|chats`,
   `data.viewAll` (скоуп чатов/почтовых ящиков). UI `/settings/users` (гейт `users.manage`):
   таблица пользователей (создание, смена роли, сброс пароля, деактивация) + таблица ролей с
   чекбокс-матрицей прав; сайдбар и суб-нав настроек скрывают пункты по правам вместо жёсткого
   `adminOnly`. Деактивация вместо удаления (блокирует login/refresh, связи Deal/Task не рвутся).
   См. CLAUDE.md, замечание 66.
8. **B14. Массовые операции (мультивыбор) + безопасное удаление этапа.** ✅ ГОТОВО (июль 2026).
   Чекбоксы + плавающий тулбар на `/deals`, `/contacts`, `/companies` и прямо на канбане (режим
   «Выбрать» отключает drag, клик выделяет вместо открытия карточки) → `POST
   /api/{deals,contacts,companies}/bulk-delete` (soft-delete `updateMany`, гейт `trash.manage`).
   Удаление этапа воронки с сделками теперь требует выбрать целевой этап — `GET
   /pipelines/stages/:id/deletion-check` считает сделки и незаполненные `requiredAtStageIds` на
   целевом этапе (предупреждение, не блокирует); перенос выставляет `closedAt`/`lostReasonId` по
   типу целевого этапа, автоматизации не триггерятся (массовый админский перенос). Заодно
   почищен регресс горизонтального скролла канбана (мышь без трекпада — `onWheel` → `scrollLeft`).
   См. CLAUDE.md, замечание 67.
9. **B15. Дедупликация контактов/компаний.** ✅ ГОТОВО (июль 2026). `services/dedup/{contacts,
   companies}.ts`. Критерии: контакты — телефон ИЛИ email (основной + доп., телефон сравнивается по
   цифрам); компании — точное имя без учёта регистра. `GET /api/{contacts,companies}/duplicates`
   (`trash.manage`) находит группы дублей; `POST /api/{contacts,companies}/merge` объединяет —
   «выживает» запись по выбранной стратегии (новая/старая по дате создания), связанные
   сделки/задачи/сообщения/абонементы/счета переносятся на неё, проигравшие уходят в корзину
   (обычный soft-delete, 30-дневный auto-purge подхватит сам). Защита при создании: `POST
   /api/{contacts,companies}` без `force: true` возвращает 409 с найденными совпадениями вместо
   создания — обрабатывается в `CreateContactModal`/`CreateCompanyModal`/`AttachContactCard`
   (последняя сразу предлагает привязать найденный контакт к сделке вместо создания дубля). UI
   поиска/объединения — кнопка «Найти дубли» на `/contacts`/`/companies` (только admin). См.
   CLAUDE.md, замечание 68.

## Бэклог (по мере надобности)

### Специфика онлайн-школы

- **A4. Связка «ученик ↔ плательщик».** Платит родитель, учится ребёнок: связь `payerId`/`students[]` у Contact; карточка сделки показывает обоих, сообщения идут плательщику.
- **A5. Расписание занятий + преподаватели.** Сущность `Lesson` (дата, ученик, преподаватель, статус: запланирован/проведён/отменён/no-show), календарный вид, списание с абонемента (A1), нагрузка преподавателей в аналитике. Опционально проброс Zoom-ссылки.
- **A7. Метрики школы в аналитике.** ⏳ ЧАСТЬ ГОТОВА (июль 2026) — конверсии + retention + источники.
  ✅ Воронка по этапам (`funnel` в `GET /api/analytics/pipeline/:id`, накопительный счёт по
  ТЕКУЩЕМУ положению сделки, `order >= N`, lost-этапы исключены) и конверсия пробный→оплата
  (`summary.trials.trialToPaymentRate` — доля сделок с завершённым пробным, у которых есть
  `Subscription`, не `Payment`, т.к. ручные оплаты наличными не создают `Payment`). Recharts
  `FunnelChart` на `/analytics`. ✅ Retention (`summary.retention`): LTV — средняя сумма всех
  подписок на ученика; renewal/churn — среди учеников с хотя бы одной ЗАВЕРШЁННОЙ подпиской
  (`exhausted`/истёк срок) доля тех, у кого есть вторая подписка (упрощённо, без проверки порядка
  во времени); НЕ зависит от диапазона дат аналитики — это метрика жизненного цикла ученика, а не
  сделок за период. ✅ Источники (`utmSources`) — объём/конверсия/выручка по
  `custom_fields.utm_source` (raw SQL, JSONB group by), пишется только лид-формой (A6), сделки без
  UTM попадают в «Без источника». ❌ Осталось: выручка по языкам/преподавателям (нет поля «язык» ни
  в схеме, ни в seed field-definitions).

### Паритет с amoCRM / Bitrix24

- **B5. Click-to-call.** `uisClient.initiateCall()` уже написан — нужен роут `POST /api/calls/initiate` + кнопка у телефона в DealModal.
- **B6. Теги** для сделок/контактов + фильтр в канбане и списках.
- **B8. Центр уведомлений.** Модель `Notification` + колокольчик с непрочитанными (socket-канал есть): новое сообщение, просроченная задача, назначение сделки.
- **B9. Глобальный поиск** (Cmd+K) по сделкам/контактам/компаниям; сначала три `contains`-запроса, позже pg_trgm.
- **B10. Файлы/вложения** в карточках (договоры, скрины оплат). S3-совместимое хранилище — диск контейнера `api` не смонтирован как volume и не переживает пересоздание/ребилд.
- **B11. Вкладка «Счета» в карточке сделки.** Сейчас `Payment` виден только компактным блоком внутри «Абонемент» (`SubscriptionCard` → `PaymentsBlock`, только счета текущей сделки). Нужна отдельная вкладка рядом с «Задачи»/«Сообщения» в DealModal с полной историей счетов контакта (в т.ч. по прошлым сделкам того же ученика) — статус, провайдер, сумма, дата оплаты, ссылка на созданный счётом абонемент. API `GET /api/payments` уже поддерживает фильтр и по `dealId`, и по `contactId` — на вкладке использовать выборку по контакту.

### Стратегические

- **C3. Генерация договора по шаблону** (docx с подстановкой полей) — договоры-оферты школ.
- **C4. Гранулярные права.** ⏳ ЧАСТЬ ГОТОВА (июль 2026) — сама матрица прав по ролям реализована как B13: любую роль (включая кастомные) можно ограничить нужным набором из 12 прав, вплоть до view-only без `entities.edit` — это уже закрывает сценарий «роль без админки». ❌ Осталось: скоуп «менеджер видит только свои сделки» (фильтр по `assigneeId` на уровне записи для deals/contacts/companies) — сознательно оставлен вне задачи 66 как отдельная, более объёмная переделка чтения списков/канбана/аналитики.
- **C5. Email-канал.** ✅ **ЧАСТЬ 1 ГОТОВА** (июль 2026): SMTP/IMAP напрямую (логин + пароль/пароль приложения, универсально для любого провайдера) — `channel: 'email'` в модели `Message` (переиспользует ленту переписки в DealModal), `EmailAccount` (общие/личные ящики, владелец + allowedUserIds), IMAP-поллинг (`services/email/imap-worker.ts`, без BullMQ — plain `setInterval`), раздел «Почта» (единый инбокс, группировка по `threadKey`), вложения через S3-совместимое хранилище (`services/storage/s3.ts`, использует и закрывает часть B10 — но только для email, не для вложений в карточках вообще). **Осталось**: (2) OAuth-вход для Яндекс/Google/Mail.ru (привязка ящика кнопкой без ручного ввода пароля приложения — отдельный OAuth-флоу и refresh-токены на каждого из трёх провайдеров); email-триггеры автоматизаций; CC/BCC в UI; rich-HTML компоновщик.
