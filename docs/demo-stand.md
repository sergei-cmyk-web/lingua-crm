# Демо-стенд (локально)

Демо-режим — тот же код, что и прод, но:
- мутации не долетают до бэкенда: перехватываются в браузере (`apps/web/src/lib/demo/`),
  изменения видны только текущему посетителю (localStorage) и никогда не сохраняются на сервере —
  `demoGuard` на бэкенде дополнительно блокирует прямые вызовы API;
- никакие внешние интеграции не вызываются по-настоящему (WazzUp/UIS/SMTP/SMS/платёжные
  провайдеры) — интерфейс мгновенно показывает «как будто отправлено»;
- фоновые воркеры (напоминания, отложенные сообщения, IMAP-поллинг) не стартуют.

**Стенд поднимается только локально, отдельного демо-деплоя нет** — показывать его нужно с ноутбука,
круглосуточно доступный публичный демо-URL не требуется.

## Запуск

```bash
docker compose -f docker-compose.dev.yml up -d      # postgres + redis
npm run db:migrate                                   # если база чистая
npm run db:seed:demo                                 # демо-данные + demo-пользователь
npm run dev:demo                                     # api с DEMO_MODE, web с NEXT_PUBLIC_DEMO_MODE
```

Открыть http://localhost:3000 — авто-логин сразу уводит в канбан, форму логина вводить не нужно.

`npm run dev:demo` — это обычный `npm run dev`, которому доклеены две переменные: `DEMO_MODE=true`
для api (`demoGuard` + воркеры выключены) и `NEXT_PUBLIC_DEMO_MODE=true` для web (клиентский
перехват мутаций). Обычный `npm run dev` в той же базе продолжает работать как всегда — демо-режим
это флаг запуска, а не отдельная установка.

Учётка демо-пользователя по умолчанию — `demo@example.com` / `demo12345` (дефолты в
`prisma/seed-demo.ts` и `lib/demo/config.ts`). Поменять — задать `NEXT_PUBLIC_DEMO_EMAIL` /
`NEXT_PUBLIC_DEMO_PASSWORD` в `.env`: их читает и seed, и форма авто-логина, поэтому менять надо
до засева, иначе учётки разъедутся и авто-логин упрётся в `401 Invalid credentials`.

Демо-данные ставятся поверх текущей локальной базы. Если нужна чистая — пересоздать том:

```bash
docker compose -f docker-compose.dev.yml down -v && docker compose -f docker-compose.dev.yml up -d
npm run db:migrate && npm run db:seed:demo
```

## Что проверить, если что-то не так

- **Форма логина вместо авто-логина** — web запущен без `NEXT_PUBLIC_DEMO_MODE` (обычный
  `npm run dev` вместо `dev:demo`).
- **`401 Invalid credentials` на экране авто-логина** — учётка: `NEXT_PUBLIC_DEMO_EMAIL`/
  `NEXT_PUBLIC_DEMO_PASSWORD` в `.env` не совпадают с тем, чем засевали, либо `db:seed:demo` вообще
  не запускался.
- **Правки сохраняются в базе** — api запущен без `DEMO_MODE=true`, `demoGuard` выключен.
  Проверить: `curl -X PATCH http://localhost:4000/api/deals/<id> -H 'Content-Type: application/json'
  -d '{"title":"hack"}'` должен вернуть `{"ok":true,"demo":true}` и НЕ изменить строку в Postgres.
- **Кнопка «Сбросить демо»** в верхнем баннере чистит localStorage-оверлей и возвращает исходные
  seed-данные — база при этом не трогается, потому что в неё ничего и не писалось.

## Кросс-ссылки между демо и продом

`NEXT_PUBLIC_DEMO_STAND_URL` (кнопка «🎭 Демо режим» под формой логина обычной сборки) и
`NEXT_PUBLIC_MAIN_APP_URL` (кнопка «← Выйти из демо» в баннере демо) — build-time переменные для
случая, когда демо и прод стоят на разных доменах. При локальном демо их задавать не нужно: обе
кнопки просто не показываются / ведут на свой же `/login`.
