# Архитектура для внедрения CRM в разные ниши

**Дата**: 2026-07-12
**Контекст**: CRM (LinguaCRM) планируется внедрять в другие ниши/проекты. Одним не нужны
абонементы, другим WazzUp, третьим SMS — либо там будут другие сервисы. Вопрос: как
устроить архитектуру, чтобы внедрять и поддерживать такие кейсы; делать ли модули и
маркетплейс.

**Вводные** (уточнены 2026-07-12): деплой — отдельный инстанс (VPS/docker-compose) на
клиента; модули включает/настраивает только своя команда; горизонт — 1–3 внедрения в
ближайший год; различия между нишами — интеграции + доменные фичи (абонементы, пробные
уроки и т.п.).

---

## Короткий ответ

**Маркетплейс не делать. Плагинную систему не делать. Форки не делать.**

Правильная конструкция на этом масштабе — три вещи, две из которых в проекте уже есть:

1. **Одна кодовая база, один `main`** — все клиенты работают на одном коде,
   различия только в конфигурации инстанса.
2. **Фича-флаги на уровне инстанса** — переменная окружения `ENABLED_MODULES`
   отключает целые разделы (роутеры + пункты сайдбара).
3. **Адаптеры провайдеров** — паттерн, который уже реализован для платёжек
   (`services/payments/`, `PaymentProvider {createLink, handleWebhook}`) и наполовину
   для сообщений (`sendViaTransport`). Новый SMS-шлюз или мессенджер = новый адаптер
   за тем же интерфейсом, а не ветка кода.

Маркетплейс — это продукт для случая «чужие люди сами подключают чужие модули».
При 1–3 внедрениях в год силами своей команды он не окупится никогда: публичный SDK,
изоляция стороннего кода, версионирование API, ревью, биллинг — всё это инфраструктура
на порядок дороже самой CRM, и ни один пункт не нужен, когда модуль включает тот же
человек, который его написал.

---

## Почему НЕ надо

| Идея | Почему нет на этом масштабе |
|---|---|
| Маркетплейс модулей | Нет сторонних разработчиков и нет self-service — некому продавать. Это бизнес-модель amoCRM с тысячами клиентов, а не инструмент для 1–3 внедрений. |
| Плагины (динамическая загрузка кода) | Динамическая загрузка нужна, только когда код модуля неизвестен на момент сборки. Здесь весь код свой и лежит в одном репозитории — обычный `if` по конфигу решает ту же задачу без рантайм-магии. |
| Форк репозитория на клиента | Через 3 месяца форки разъезжаются, и каждый багфикс (а их в проекте много — см. замечания 44, 49–52 в CLAUDE.md) приходится портировать руками в каждый форк. Это самый дорогой вариант поддержки из существующих. |
| Мультитенантный SaaS | Решение «инстанс на клиента» уже принято, и оно правильное для этого масштаба: изоляция данных бесплатно, тарифы/лимиты не нужны, `tenantId` не нужно протаскивать через каждый запрос и каждую таблицу. |
| Микросервисы | 10–50 менеджеров на инстанс. Монолит Express — правильный размер. |
| Отдельная schema.prisma на клиента | Расхождение миграций между инстансами — источник вечной боли. Схема одна для всех, см. ниже. |

---

## Целевая архитектура: три слоя различий

Различия между нишами раскладываются на три типа, и у каждого свой механизм.
Смешивать их не надо.

### Слой 1. Доменные модули — фича-флаги (`ENABLED_MODULES`)

Доменные блоки, которые нужны не всем: `subscriptions` (абонементы + пакеты + уроки),
`trials` (пробные уроки + напоминания), `payments` (счета + вебхуки оплат), `email`
(почта), `chats`, `analytics`.

Механизм — одна env-переменная на инстанс:

```env
# .env клиента «онлайн-школа» (текущий LinguaCRM)
ENABLED_MODULES=subscriptions,trials,payments,email,chats,analytics

# .env клиента «агентство» — только ядро + чаты
ENABLED_MODULES=chats,analytics
```

Реализация — минимальная, без реестров и манифестов:

- **Бэкенд**: в `index.ts` роутеры модуля монтируются условно:
  `if (moduleEnabled('subscriptions')) app.use('/api/subscriptions', ...)`.
  Выключенный модуль = 404 на всех его роутах. Хелпер `moduleEnabled()` — 3 строки,
  парсит env один раз.
- **Фронтенд**: `GET /auth/me` (или `/health`) дополнительно отдаёт список включённых
  модулей; сайдбар и вкладки DealDetail фильтруются по нему — тот же механизм, что уже
  работает для прав (`useHasPermission()`, сайдбар-пункты с `permission`). Это второй
  фильтр рядом с существующим, не новая система.
- **Ядро не флагуется**: deals, contacts, companies, tasks, pipelines, канбан,
  кастомные поля, автоматизации, роли — есть у всех, всегда.

**База данных — одна схема для всех инстансов, включая таблицы выключенных модулей.**
Пустая таблица `Subscription` у клиента без абонементов не стоит ничего, а
единая линейка миграций на все инстансы — это главное, что делает поддержку
N инстансов дешёвой: деплой везде одинаковый (`prisma migrate deploy`), никаких
«у клиента X другая схема».

### Слой 2. Интеграции-провайдеры — адаптеры за общим интерфейсом

Это случай «SMS нужна, но не TargetSMS» или «мессенджеры нужны, но не через WazzUp».
Тут флаг не поможет — нужна замена реализации. Паттерн в проекте уже есть, его надо
просто распространить:

- **Платёжки — уже сделано правильно**: `services/payments/` с интерфейсом
  `PaymentProvider {createLink, handleWebhook}` и `getProvider(name)`; CloudPayments и
  Робокасса — два адаптера. Новый эквайринг = третий файл-адаптер, ноль изменений в
  роутах и UI.
- **SMS — довести до того же вида**: сейчас `sendViaTransport` захардкожен на
  `sms → TargetSMS`. Выделить интерфейс `SmsProvider {send, getBalance, getTemplates?}`,
  TargetSMS — первый адаптер, выбор провайдера — ключ в `IntegrationSetting`
  (`sms.provider`), по образцу `payments.defaultProvider`.
- **Мессенджеры — то же, но только когда появится второй провайдер**: WazzUp сейчас
  единственный шлюз, и абстрагировать его заранее не надо (YAGNI). Когда придёт клиент
  с другим шлюзом — граница уже видна: всё проходит через `sendViaTransport` /
  `sendMessageToContact` и вебхук `webhooks/wazzup.ts`; интерфейс
  `MessengerProvider {sendMessage, parseWebhook}` выделяется в этот момент, а не сейчас.
- Интеграция без кредов и так уже фактически выключена (тест подключения, `hasValue`
  у секретов) — отдельные флаги для интеграций не нужны, «не настроено = не работает»
  достаточно. Прятать страницу настроек ненастроенной интеграции — опционально, через
  тот же `ENABLED_MODULES`.

### Слой 3. Настройки ниши — то, что уже конфигурируется без кода

Значительная часть «отличий ниши» в этой CRM уже не требует кода — это надо
использовать в первую очередь при внедрении:

- **Кастомные поля** (`field_definitions` + JSONB) — предметные атрибуты сделки/контакта
  («уровень языка» у школы, «площадь объекта» у агентства недвижимости) — создаются из UI.
- **Воронки и этапы** (мульти-воронки, типы этапов won/lost, причины потери) — процессы
  ниши моделируются этапами, не кодом.
- **Автоматизации** (конструктор + BullMQ-движок) — «после этапа X создать задачу /
  отправить сообщение» — из UI.
- **Роли и права** (матрица permissions) — состав команды ниши.
- **Шаблоны сообщений, лид-форма, офсеты напоминаний** — через `IntegrationSetting`.

Правило при запросе от нового клиента: **сначала слой 3 (конфиг из UI), потом слой 2
(новый адаптер), потом слой 1 (новый модуль за флагом), и только потом — новая
сущность в ядре.** Новая доменная сущность («брони», «объекты») — это новый модуль:
свои таблицы, свой роутер, свой раздел UI, всё за своим флагом, ядро не трогается.

## Как выглядит внедрение нового клиента

1. Новый VPS, тот же `docker-compose.yml` (ранбук уже есть — `docs/vps-migration.md`).
2. `.env`: домен, секреты, `ENABLED_MODULES` под нишу.
3. Из UI: воронки, этапы, кастомные поля, роли, автоматизации, шаблоны.
4. Креды интеграций клиента в `/settings/*` (его WazzUp/SMS/платёжка — или ничего).
5. Если нужен другой провайдер — написать адаптер (попадает в общий `main`, доступен
   всем будущим клиентам).
6. Деплой — тот же GitHub Actions workflow, добавляется хост клиента
   (matrix по серверам или отдельный workflow-файл на клиента — решить при втором
   реальном внедрении, не раньше).

Обновления: один `main` → пуш → деплой на все инстансы. Клиент, которому фича не нужна,
получает её выключенной флагом — код везде одинаковый, поведение разное.

## Что нужно сделать в коде (по мере надобности, не заранее)

**Перед первым внедрением в другую нишу — и не раньше:**

1. `ENABLED_MODULES` + `moduleEnabled()` + условный монтаж роутеров в `index.ts`
   (~30 строк). Импорты воркеров модуля (`trial-reminders`, `scheduled-messages`) —
   под тот же флаг.
2. Список модулей в ответе `/auth/me` + фильтр сайдбара/вкладок на фронте
   (по образцу permission-гейтов).
3. Прогнать текущий инстанс с полным списком модулей — поведение не должно измениться.

**Когда придёт клиент с другим SMS/мессенджером/платёжкой:**

4. Выделить интерфейс провайдера по образцу `services/payments/` и завести адаптер.

**Никогда (пока не изменятся вводные):**

- Реестр модулей, манифесты, динамическая загрузка, версионирование модулей,
  маркетплейс, биллинг модулей, публичный SDK.

## Триггеры для пересмотра решения

Архитектура выше рассчитана на текущие вводные. Пересматривать, если:

| Сигнал | Что менять |
|---|---|
| Инстансов стало 5+ и их поддержка съедает заметное время | Централизованный мониторинг всех инстансов, деплой-matrix, возможно общий admin-панель статусов. Всё ещё не SaaS. |
| Появились мелкие клиенты, которым дорог отдельный VPS | Тогда — мультитенантность (`organizationId` в схеме). Это большой рефакторинг; делать только под реальный поток таких клиентов. |
| Клиенты хотят сами включать модули и платить за них | Тогда флаги переезжают из env в БД + UI-каталог. «Маркетплейс» без сторонних разработчиков — это просто страница настроек с чекбоксами и биллингом. |
| Сторонние разработчики хотят писать модули | Единственный случай, когда нужен настоящий маркетплейс/SDK. До этого сигнала — не проектировать. |

Суть: каждая ступень усложнения включается по реальному сигналу рынка, а не заранее.
Текущая кодовая база к каждой ступени готова ровно настолько, насколько нужно, —
границы модулей уже проведены структурой `routes/` + `services/`, и это единственная
«подготовка к будущему», которая ничего не стоит сейчас.
