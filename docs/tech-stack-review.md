# Ревью технологического стека: 100 одновременных пользователей, 500 тыс. записей каждой сущности

**Дата:** 2026-07-12
**Вопрос:** правильно ли выбраны языки/технологии, если одновременно в системе до 100 пользователей, а сделок, контактов и компаний — до 500 тыс. каждой сущности (~1.5+ млн строк ядра, плюс messages/activities, которые растут быстрее всего).
**Метод:** анализ реального кода (пути и строки указаны), а не абстрактная оценка технологий.

---

## Резюме

**Стек выбран правильно. Менять язык не нужно.**

Node.js/TypeScript + Express + PostgreSQL 16 + Prisma + Redis/BullMQ + Socket.io — стандартный, взаимно совместимый набор именно для такого профиля нагрузки: CRM — это I/O-bound система (95% работы — ожидание БД, вебхуков WazzUp/UIS, SMTP/IMAP, платёжных провайдеров), а не вычисления. 100 одновременных пользователей — это единицы-десятки HTTP-запросов в секунду; Node в одном процессе спокойно держит на порядки больше. 1.5 млн строк — маленькая база для PostgreSQL: при правильных индексах такие таблицы обслуживаются миллисекундными запросами.

Ни одно из найденных узких мест (см. раздел 3) не является следствием выбора языка — все они лежат в конкретных запросах и в компоновке процессов, и все чинятся точечно внутри текущего стека: индексами, лимитами, пагинацией. Переписывание на Go/Java не устранило бы ни одного из них — неиндексированный `ORDER BY createdAt` по 500 тыс. строк одинаково медленный из любого языка.

Что реально требует внимания до роста базы (приоритет сверху вниз): канбан без лимитов, экспорт в память, «Чаты» без пагинации, отсутствующий кэш аналитики, недостающие индексы.

## 1. Оценка компонентов стека

### Node.js + Express (backend) — ✅ подходит

Профиль нагрузки CRM — I/O-bound: каждый запрос это 1–5 обращений к Postgres плюс изредка внешние API. Event loop Node создан ровно под это. 100 одновременных пользователей CRM генерируют в пике ~10–30 RPS (менеджеры читают карточки, а не грузят систему непрерывно) — запас у одного процесса Node многократный.

Единственный реальный риск для Node — CPU-bound задачи, блокирующие event loop, и такие в коде есть: сборка XLSX через ExcelJS при экспорте (`services/export/deals.ts`) и dedup-группировка в JS (`services/dedup/contacts.ts`). При 500 тыс. строк один такой запрос замораживает **все** остальные запросы и Socket.io-события, потому что всё живёт в одном процессе (см. риск №7). Это чинится выносом в worker/стриминг, не сменой языка.

### PostgreSQL 16 — ✅ подходит с запасом

1.5 млн строк ядра + несколько миллионов messages/activities — обычный объём для одиночного Postgres, до его реальных пределов (сотни миллионов строк) далеко. JSONB для `custom_fields` — правильное решение для гибкой схемы; при появлении частых фильтров по кастомным полям нужен GIN-индекс (уже предусмотрено в CLAUDE.md, замечание 5).

Проблема не в Postgres, а в недостающих индексах: **ни на одной из основных таблиц нет индекса `createdAt`**, при том что это дефолтная сортировка всех списков и канбана (`schema.prisma` — Deal имеет индексы на `pipelineId/stageId/assigneeId/contactId/lostReasonId/deletedAt`, но не на ключ сортировки). На 10 тыс. сделок это незаметно; на 500 тыс. каждая страница списка — сортировка большого набора без индекса, а offset-пагинация (`skip/take`, `deals.ts:49-69`) деградирует линейно с глубиной страницы.

### Prisma ORM — ✅ подходит, одна настройка

Prisma 5 генерирует адекватный SQL для всех паттернов проекта (включая `distinct`+`orderBy` для инбоксов). Два нюанса:

- **Пул соединений**: дефолт Prisma — `num_cpus × 2 + 1`, на 2 vCPU это 5 соединений на процесс. Для 100 одновременных пользователей это узко — запросы будут вставать в очередь за соединением. Лечится параметром `?connection_limit=20` в `DATABASE_URL` (одна строка в `.env`).
- Тяжёлый `dealInclude` (contact + phones + emails + channels + trials на каждую строку) умножает стоимость каждой выборки списка — терпимо при `take: 50`, опасно в unbounded-запросах.

### Redis + BullMQ (очереди) — ✅ подходит

Архитектура очередей грамотная: delayed-джобы вместо поллинга, детерминированные jobId для O(1)-отмены, reconciliation-sweep с источником истины в Postgres, fire-and-forget вне критического пути HTTP (замечания 31, 33 CLAUDE.md). Нагрузка на очереди пропорциональна событиям (переносы сделок, напоминания), а не размеру базы — 500 тыс. записей сами по себе очередей не касаются. Redis свой, в контейнере рядом с API — лимитов на число команд нет.

### Socket.io (реалтайм) — ✅ подходит для 100 пользователей

Обработчики комнат не делают работы с БД (`socket/handlers.ts` — чистые join/leave), рассылка идёт адресно в комнаты `pipeline:{id}`/`deal:{id}`/инбоксы. 100 одновременных подключений для Socket.io — ничто (штатно держит тысячи).

Ограничение на будущее: Redis-адаптера для Socket.io нет (`ioredis` используется только BullMQ), поэтому API нельзя горизонтально масштабировать на несколько инстансов — комнаты не синхронизируются между процессами. Для 100 пользователей это не нужно; если понадобится — `@socket.io/redis-adapter` ставится за час, Redis уже есть.

### Next.js 14 + React (frontend) — ✅ подходит

Фронтенд-нагрузка от 100 пользователей размазана по их браузерам — серверу Next достаётся только SSR/статика, это не узкое место. TanStack Query + оптимистичные обновления + сокет-инвалидация — правильный современный паттерн.

Риск один, и он парный к бэкенд-риску №1: `KanbanBoard.tsx` держит **все** сделки воронки в стейте одним запросом. При 100–200 тыс. сделок в воронке вкладка канбана будет получать десятки мегабайт JSON и рендерить десятки тысяч DOM-карточек — браузер умрёт раньше сервера.

### Общий TypeScript (packages/shared) — ✅ сильный аргумент за текущий стек

Один язык на фронте и бэке даёт общие типы сущностей и констант (`packages/shared`) — сейчас типы Deal/Contact/Trial/Automation гарантированно синхронны между API и UI. При смене языка бэкенда это преимущество теряется полностью (нужна кодогенерация OpenAPI или ручная синхронизация — постоянный источник багов).

### Инфраструктура: VPS 2 vCPU / 4 ГБ — ⚠️ хватит, но впритык

Для 100 пользователей при **починенных** запросах — достаточно. Но: один контейнер `api` без лимитов ресурсов, без кластеризации, и в этом же процессе живут Socket.io, все BullMQ-воркеры и IMAP-поллинг (`index.ts` импортирует воркеры напрямую). Postgres на 1.5+ млн строк захочет больше памяти под кэш страниц. План масштабирования простой и дешёвый: (1) VPS до 4 vCPU / 8 ГБ (вертикально), (2) воркеры в отдельный контейнер тем же docker-compose. Ни то, ни другое не требует изменений архитектуры.

## 2. Узкие места при росте до 500 тыс. записей

Ранжировано по тому, что сломается первым. Все пункты — свойства конкретного кода, не стека.

| # | Проблема | Где | Что произойдёт при 500k |
|---|----------|-----|--------------------------|
| 1 | **Канбан грузит все сделки воронки** без лимита, с полным `dealInclude`; фронт держит всё в стейте | `deals.ts:150` (`/kanban/:pipelineId`, nested `deals` без `take`), `KanbanBoard.tsx` | Ответ в десятки МБ, секунды на запрос, блокировка event loop на сериализации, падение вкладки браузера. Ломается первым — уже при ~20–50 тыс. сделок в воронке |
| 2 | **Экспорт сделок целиком в память** (ExcelJS собирает весь workbook в RAM, CSV тоже буферизуется) | `deals.ts:90` (`/export`, `findMany` без `take`), `services/export/deals.ts` | Экспорт всех сделок = сотни МБ в памяти процесса → OOM-kill контейнера api, падают все пользователи разом |
| 3 | **«Чаты» — unbounded `distinct` по всей таблице messages** без пагинации; плюс нет индекса `(contactId, createdAt)` / `readAt` | `chats.ts:23` (`distinct: ['contactId']`, без `take`) | Каждое открытие раздела — скан/сортировка всей таблицы сообщений. «Почта» (`email.ts:36`) пагинирована — асимметрия, чинить по её образцу |
| 4 | **Кэш аналитики не реализован** (в CLAUDE.md заявлен «кэш в Redis на 5 минут» — в коде его нет); per-stage суммы бюджета считаются загрузкой всех сделок в JS | `analytics.ts` (15 запросов в `Promise.all`, nested `deals{select: budget}` без `take`; ни одного упоминания redis/cache в файле) | Каждый заход руководителя на /analytics — полный прогон по 500 тыс. строк, включая загрузку всех budget в память |
| 5 | **Нет индексов `createdAt`** на Deal/Contact/Company/Message/Activity | `schema.prisma` | Дефолтная сортировка каждого списка — без индекса; deep-offset страницы деградируют линейно |
| 6 | **Dedup — full-table scan** всех контактов с нормализацией в JS | `services/dedup/contacts.ts:25` (собственный `ponytail:`-коммент называет порог «well past 10k» — 500k превышает его в 50 раз) | Кнопка «Найти дубли» грузит 500 тыс. контактов с телефонами/email в память и строит граф в JS — минуты работы + блокировка event loop |
| 7 | **Один Node-процесс на всё**: API + Socket.io + 3 BullMQ-воркера + IMAP-поллинг; в compose нет лимитов ресурсов | `index.ts` (импорт воркеров), `docker-compose.yml` | Любая тяжёлая задача (экспорт, dedup, sweep) тормозит HTTP и реалтайм для всех; OOM одного компонента убивает все |
| 8 | **Поиск `ILIKE '%…%'`** по name/title без pg_trgm-индекса; `limit` из query не ограничен сверху (`?limit=999999` обходит пагинацию на любом списке) | `deals.ts:56`, `contacts.ts:21`, `companies.ts:15` | Каждый поиск — sequential scan по 500 тыс. строк; невалидированный limit — самодельный DoS одним запросом |

## 3. Рекомендации (в порядке внедрения)

Всё ниже — точечные правки в текущем стеке. Ни один пункт не требует смены технологий.

**Сейчас (дёшево, до любого роста):**
1. Индексы: `Deal/Contact/Company` — `@@index([deletedAt, createdAt])`; `Message` — `@@index([contactId, createdAt])` и `@@index([readAt])`; `Activity` — `@@index([dealId, createdAt])`. Одна миграция.
2. Clamp на `limit` во всех списках: `Math.min(Number(limit) || 50, 200)`.
3. `?connection_limit=20` в `DATABASE_URL`.

**До ~50 тыс. сделок:**
4. Канбан: `take: N` (50–100) на колонку + кнопка/скролл «показать ещё» (так работает amoCRM, которую система замещает). Это самая важная правка из всех.
5. «Чаты»: пагинация по образцу `email.ts` (там уже правильный `skip/take`).
6. Аналитика: реализовать заявленный Redis-кэш (Redis уже подключён, ~15 строк кода) + заменить nested `findMany` бюджета на `groupBy` c `_sum` на стороне Postgres.

**До ~100–200 тыс. записей:**
7. Экспорт: стриминговый CSV (`csv-stringify` умеет pipe в response) вместо буферизации; XLSX — либо лимит строк, либо генерация в воркере.
8. Dedup: выполнить upgrade path из собственного `ponytail:`-комментария — нормализованные колонки телефона/email + индекс, поиск дублей через SQL `GROUP BY` вместо загрузки таблицы в JS.
9. Поиск: расширение `pg_trgm` + GIN-индекс на `Contact.name`/`Deal.title` (одна миграция с raw SQL).
10. Инфраструктура: воркеры (BullMQ + IMAP) в отдельный контейнер `worker` в том же compose (отдельный entrypoint, тот же образ) — тяжёлые фоновые задачи перестают конкурировать с HTTP/Socket.io.

**Чего делать НЕ нужно:**
- Переписывать бэкенд на другой язык — не решает ни одного пункта выше.
- Шардировать/партиционировать Postgres — не тот масштаб (актуально с сотен миллионов строк).
- Elasticsearch для поиска — pg_trgm покрывает задачу на этом объёме.
- Микросервисы — монолит + отдельный worker-контейнер это потолок необходимой декомпозиции здесь.

## 4. Сравнение с альтернативными языками

**Go.** Выигрыш — в CPU-bound задачах и экономии памяти на десятках тысяч одновременных соединений. Здесь нет ни того, ни другого: нагрузка I/O-bound, соединений ~100. Цена перехода — переписывание всего бэкенда (~30+ роутов, движок автоматизаций, 6 интеграций с внешними API), потеря Prisma-миграций и общих TS-типов с фронтом, более дорогой найм. Единственные CPU-точки проекта (экспорт, dedup) чинятся в Node выносом в воркер за дни, а не месяцы переписывания.

**Java / C# (.NET).** Те же аргументы, что для Go, плюс тяжелее рантайм (важно на VPS 4 ГБ, где уже живут Postgres + Redis + Next). Оправданы в энтерпрайзе с большими командами и строгими требованиями — не профиль школы с 10–50 менеджерами.

**Python (Django/FastAPI).** Не дал бы даже теоретического выигрыша в производительности (GIL, интерпретатор медленнее V8), а стоил бы тех же общих типов. Имел бы смысл только при тяжёлой ML-составляющей — её нет (AI-фичи из ROADMAP пойдут через внешние API, языку бэкенда безразлично).

**Вывод:** все найденные узкие места — про запросы к БД и компоновку процессов. Они инвариантны к языку: канбан, тянущий 500 тыс. строк без лимита, положит сервис на Go точно так же. Правильная инвестиция — пункты раздела 3, а не смена стека.
